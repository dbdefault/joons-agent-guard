# 보장 범위 — joons_agent_guard 0.1.0

English original: [docs/guarantees.md](../guarantees.md)

이 문서는 구성 요소별로 이 라이브러리가 보장하는 것과 명시적으로 보장하지 **않는** 것을 설명합니다. 또한 각 장애 상황의 복구 방법을 설명합니다. 여기의 모든 내용은 `joons_agent_guard.lock`, `joons_agent_guard.circuit`, `joons_agent_guard.replay`, `joons_agent_guard._db`, `joons_agent_guard.errors` 소스에서 도출했습니다. 그리고 정확히 이 코드를 대상으로 스크립트로 만든 확인 절차(probe)를 돌려 검증했습니다.

범위: 세 구성 요소는 모두 **SQLite 데이터베이스 파일 하나를 함께 쓰는** 프로세스들을 조율합니다. 이 파일 묶음을 조정 영역(coordination domain)이라고 부릅니다. `:memory:`는 인스턴스마다 따로 존재하는 사적 영역입니다. 아래의 모든 보장은 한 영역 안에서, 한 컴퓨터 위에서, 로컬 파일 시스템 위에서만 성립합니다.

---

## 1. 모든 구성 요소에 공통인 기본 규칙

### 보장하는 것

1. **쓰기는 원자적(atomic)입니다.** 여러 문장으로 이루어진 모든 변경은 `_db.write_txn`을 통해 `BEGIN IMMEDIATE ... COMMIT` 트랜잭션(transaction) 안에서 실행됩니다. 예외가 생기면(`BaseException`도 포함이므로 `KeyboardInterrupt`도 포함입니다) 트랜잭션을 롤백(rollback)하고 예외를 그대로 다시 던집니다. 실패한 호출 뒤의 저장 상태는 호출 전과 정확히 같습니다.
2. **상태는 영속적(durable)입니다.** 모든 상태는 SQLite 파일 안에 있으므로 프로세스가 멈추거나 다시 시작되어도 남습니다. 같은 경로를 다시 열면 같은 상태를 봅니다.
3. **아무것도 나이로 만료되지 않습니다.** TTL도 없고, 뒤를 돌보는 청소 절차도 없고, 나이를 검사하는 코드 경로도 없습니다. 시각 값(`acquired`, `updated`, `ts`)은 사람이 보라고 기록합니다. 무엇을 무효화할지 판단하는 데는 쓰이지 않습니다(`docs/architecture.md`의 "Why nothing expires by age"를 참고하십시오).
4. **식별자 검증.** 식별자 인자(`resource`, `owner`, `job_id`, `actor`, `principal`, `request_id`, `digest`, `intent_id`, `expected_job_id`)는 비어 있지 않은 `str`이어야 합니다. 그렇지 않으면 데이터베이스를 건드리기 **전에** `InvalidIdentifier`가 발생합니다. 이 예외는 `GuardError`와 `ValueError`를 모두 물려받았습니다. 검증이 절반만 쓰인 상태를 남길 일은 없습니다.
5. **쓰기는 한 줄로 섭니다.** `BEGIN IMMEDIATE`는 처음부터 데이터베이스 쓰기 잠금을 잡습니다. 그래서 프로세스를 넘나드는 동시 쓰기는 한 줄로 섭니다. 쓰기들은 서로 섞이지 않고 바쁨 대기 시간(busy timeout)만큼 기다립니다.
6. **오류 규율.** 잘못된 사용은 `GuardError`를 물려받은 예외(`InvalidIdentifier`, `LockHeld`, `IntentMismatch`)를 냅니다. 트랜잭션이 열려 있는 인스턴스에 또 쓰면 평범한 `GuardError`가 납니다(항목 7). SQLite 수준의 실패는 호출에서 `sqlite3` 예외(보통 `OperationalError`)로 나옵니다. 라이브러리는 오류를 삼키지 않습니다. 내부에서 조용히 다시 시도하지도 않습니다.
7. **겹쳐 쓰기는 없습니다.** 인스턴스에 트랜잭션이 열려 있는 동안에는, 특히 `apply_pending` 효과(effect) 안에서는, 이 인스턴스의 쓰기 메서드를 부를 수 없습니다. 부르면 데이터베이스를 건드리기 전에 `GuardError`가 납니다. 진행 중인 트랜잭션은 거절된 호출의 영향을 받지 않습니다. 효과가 이 오류를 밖으로 흘려보내면 바깥 트랜잭션은 평소처럼 롤백됩니다.
8. **인스턴스는 스레드 안전(thread-safe)합니다.** 모든 쓰기 트랜잭션과 모든 읽기, `close()`는 연결의 재진입 잠금(re-entrant lock)을 거칩니다. 그래서 인스턴스 하나를 여러 스레드가 함께 쓸 수 있습니다. 서로 다른 스레드의 문장이 한 트랜잭션 안에서 섞이는 일은 없습니다(`tests/test_threads.py`). 공유 인스턴스는 호출을 한 줄로 세웁니다.

### 보장하지 않는 것

1. **네트워크 파일 시스템.** 두 대의 컴퓨터가 네트워크 드라이브로 DB 파일을 함께 쓰면 모든 보장이 무효가 됩니다(§5 참고).
2. **동시에 실행하기.** 공유 인스턴스는 호출을 한 번에 하나씩 처리합니다. 스레드 안전은 직렬화에서 나오지, 동시 실행에서 나오지 않습니다. 읽기를 병렬로 하려면 같은 파일에 대해 스레드마다 인스턴스를 따로 주십시오. 그래도 SQLite의 쓰기는 한 번에 하나만 허용됩니다.
3. **신원 확인.** `owner`, `actor`, `principal`은 받은 그대로 기록하는 평범한 문자열입니다. 누가 부르는지 확인하는 것은 없습니다. `replay.py`의 자체 문서도 principal은 신뢰할 수 있는 통신 경로에서 와야 한다고 말합니다.
4. **성능이나 가용성.** 파일은 하나입니다. 쓰기는 한 번에 하나입니다.

### 인프라 수준의 장애(모든 구성 요소에 적용)

| 장애 | 확인된 동작 | 권장 복구 방법 |
|---|---|---|
| **DB 바쁨 대기 시간 초과** — 다른 쓰기가 `timeout`(기본값은 `ResourceLock`/`CircuitBreaker`는 10초, `ReplayGuard`는 15초)보다 오래 쓰기 잠금을 쥐고 있습니다 | 호출이 `sqlite3.OperationalError`("database is locked")를 냅니다. 상태는 변하지 않습니다 | 잠시 뒤 다시 시도하십시오. `timeout`을 크게 해서 다시 만들어도 됩니다. 쓰기 경쟁을 줄이십시오. 내부의 재시도는 없습니다 |
| **디스크가 가득 참** | 호출이 `sqlite3.OperationalError`를 냅니다. 트랜잭션이 롤백되므로 절반만 쓰인 행은 없습니다(`PRAGMA max_page_count`로 `SQLITE_FULL`을 강제해서 확인했습니다). 원래의 "database or disk is full" 오류가 그대로 나옵니다. 실패한 `COMMIT`도 롤백되므로 연결은 계속 쓸 수 있습니다(`tests/test_txn.py`의 회귀 시험) | 공간을 확보하고 다시 시도하십시오(인스턴스를 계속 쓸 수 있음을 확인했습니다). 커밋 시점의 실패가 의심되면 인스턴스를 닫았다 다시 열고 `PRAGMA integrity_check`를 실행하십시오 |
| **두 컴퓨터가 네트워크 드라이브 하나를 함께 사용** | 이 경우는 보장의 밖입니다. SQLite의 프로세스 간 잠금은 믿을 수 있는 파일 잠금(file locking)을 필요로 합니다. 네트워크 파일 시스템은 이를 제공하지 않습니다(SQLite 문서 자신이 NFS에서는 깨진다고 말하고, SMB에서도 약합니다). 최악에는 갱신이 사라지거나 파일이 망가집니다 | 이렇게 하지 마십시오. DB는 컴퓨터마다 로컬 디스크에 두십시오. 여러 컴퓨터를 조율하려면 이 패키지가 아니라 서버급 데이터베이스를 쓰십시오. 이미 일이 나면 `PRAGMA integrity_check`를 실행하고, 실세계의 결과물을 하나씩 대조해 맞추십시오. 패키지는 다시 틀어 놓을 거래 기록을 저장하지 않습니다 |

## 2. ResourceLock

이름 붙인 자원(resource)에 대한 배타적 잠금(lock)입니다. `(owner, job_id)` 쌍이 잠금을 쥡니다. 상태는 `resource_locks` 표에 잠금마다 한 행씩입니다. 행이 없으면 자원은 놓인 것입니다.

### 보장하는 것

1. **자원별 상호 배제(mutual exclusion).** `resource`는 기본 키(primary key)입니다. `acquire`는 `BEGIN IMMEDIATE` 안에서 `INSERT OR IGNORE`로 삽입합니다. 행을 실제로 삽입했을 때만 `True`를 돌려줍니다. 조정 영역 전체에서 어느 시점이든 잠금자는 많아야 하나입니다.
2. **재진입은 없습니다.** 쥐고 있는 상태에서 다시 잠그면 `False`를 돌려줍니다. 같은 `(owner, job_id)`라도 마찬가지입니다.
3. **놓으려면 셋이 정확히 맞아야 합니다.** `release`는 `(resource, owner, job_id)`가 정확히 맞을 때만 삭제합니다. 삭제에 성공했을 때만 `True`를 돌려줍니다. owner가 틀리거나 `job_id`가 틀리거나 자원이 없으면 `False`를 돌려주고 잠금은 그대로입니다.
4. **강제 해제는 job-id로 확인합니다.** `break_lock`은 `expected_job_id`가 저장된 값과 맞을 때만 삭제합니다. 사이에 새 작업이 잠금을 다시 잡았다면 그 잠금은 지워지지 않습니다. `owner`는 일부러 무시합니다. 이것은 운영자의 복구 절차이기 때문입니다. 자원 이름과 현재 `job_id`를 아는 사람이면 누구든 해제할 수 있습니다.
5. **`hold()`의 규율.** 컨텍스트 관리자(context manager)에 들어가면 잠그거나 `LockHeld`를 냅니다. 이 예외는 `.resource`와 `.holder`(현재 잠금자의 `LockInfo` 스냅숏)를 갖고 있습니다. 자원이 바쁘면 본문은 절대 실행되지 않습니다. 놓는 것은 `finally`에서 일어납니다. 따라서 정상 종료에서도 예외에서도 놓습니다.
6. **가시성.** `status`는 `None`이나 `LockInfo`(`resource`, `owner`, `job_id`, `acquired_at`)를 돌려줍니다. `list_locks`는 모든 잠금을 `acquired` 오름차순으로 돌려줍니다. 둘 다 커밋된 상태를 읽습니다.
7. **영속, 만료 없음.** 잠금은 파일을 닫았다 다시 열어도 살아 있습니다. 저절로 만료되지 않습니다. 잠금이 끝나는 길은 `release`(셋 일치)와 `break_lock`(job-id 일치)뿐입니다.

### 보장하지 않는 것

1. **살아 있음.** 잠금을 쥔 채로 멈춘 작업자는 자원을 영원히 막아 둡니다. 죽음을 알아채는 것은 없습니다. 복구는 언제나 명시적인 `break_lock`입니다.
2. **울타리(fencing).** 이 잠금은 약속일 뿐입니다. 잠금을 쥐고 있어도 누군가 자원을 만지는 것을 막지는 못합니다. 모든 참여자가 행동 전에 이 라이브러리를 거쳐야만 상호 배제가 성립합니다.
3. **공정함이나 줄 서기.** `acquire`는 해 보고 안 되면 포기합니다. 대기 줄도 없고 순서 약속도 없습니다.
4. **엄밀한 시간 순서.** `list_locks`는 벽시계 기준의 `acquired`로 정렬합니다. 한 시계 눈금 안의 두 잠금은 시각이 같아 순서가 묶일 수 있습니다.

### 장애 상황과 복구

| 상황 | 멈춘 뒤의 저장 상태 | 권장 복구 방법 |
|---|---|---|
| **잠금을 쥔 채 작업 시작 전에 멈춤**(잠금은 걸었고 일은 시작하지 않음) | 잠금 행은 그대로입니다. 잠금자는 사라졌습니다 | 운영자가 작업이 실행되지 않았음을 확인합니다 → `break_lock(resource, job_id)` → 다시 잠그고 실행합니다 |
| **작업 후 놓기 전에 멈춤**(일은 했고 잠금은 안 놓음) | 잠금 행은 그대로입니다. 작업의 결과는 라이브러리에 알려져 있지 않습니다 | 작업이 끝났는지 라이브러리 밖에서 확인합니다 → `break_lock(resource, job_id)` 또는 아는 셋으로 `release` → 작업은 **다시 실행하지 않습니다** |
| 바쁨 대기 시간 초과 / 디스크 가득 / 네트워크 드라이브 | 상태는 변하지 않습니다 / 부분 행은 없습니다 / 보장은 무효가 됩니다 | §1의 인프라 수준 장애를 보십시오 |

## 3. CircuitBreaker

작업자(actor)마다 **실행 자리(run slot) 하나**에 마지막 결과 기억을 더한 도구입니다. 중요한 점이 있습니다. 이것은 전형적인 임계값과 휴지 시간을 쓰는 회로 차단기가 아닙니다. `open` 상태는 그 자체로 시작을 막지 않습니다. `open` 뒤의 다음 `begin`이 곧 유일한 회복 시도(`half_open`)입니다. `failures`는 계수기이지 차단 기준이 아닙니다.

상태는 `worker_circuits.state`에 `closed`, `open`, `half_open`으로 저장됩니다. 진행 중인 작업은 `pending`(즉 `job_id`)에 기록됩니다. `half_open`에는 항상 진행 중인 작업이 있습니다.

### 보장하는 것

1. **작업자마다 진행 중인 작업은 하나입니다.** 어떤 작업이 이미 진행 중이거나 상태가 `half_open`이면 `begin`은 `False`를 돌려줍니다. 그렇지 않으면 자리를 차지합니다. 새 actor나 `closed` actor는 `pending = job_id`인 `closed`가 됩니다. `open` actor는 `half_open`(회복 시도)이 됩니다.
2. **진행 중인 작업만 끝낼 수 있습니다.** `finish`는 `actor`와 `pending = job_id`가 모두 맞는 행만 고칩니다. 그렇지 않으면 `False`를 돌려주고 아무것도 바꾸지 않습니다(모르는 actor, 틀린 작업, 이미 끝난 작업).
3. **결과 기록.** `finish(success=True)`는 상태를 `closed`로 하고, `failures = 0`으로 하고, reason을 지웁니다. `finish(success=False)`는 상태를 `open`으로 하고, `failures`를 하나 올리고, `reason`을 저장합니다. 그래서 `consecutive_failures`는 연속된 실패 횟수입니다. 이 값은 성공이나 `reset`으로만 0이 됩니다.
4. **운영자 리셋도 job-id로 확인합니다.** `reset(actor, expected_job_id)`는 그 작업이 아직 진행 중일 때만 적용됩니다. 다른 진행 중인 작업을 덮어쓸 수 없습니다. `reset(actor)`는 조건 없이 지웁니다. 둘 다 상태를 `closed`로, 진행 중 작업을 없음으로, `failures = 0`으로, reason을 없음으로 만듭니다. 둘 다 행을 실제로 고쳤을 때만 `True`를 돌려줍니다. 한 번도 begin하지 않은 actor는 `False`를 돌려줍니다.
5. **가시성.** `snapshot`은 `CircuitState`(`state`, `pending_job`, `consecutive_failures`, `last_failure_reason`)를 돌려줍니다. 행이 없는 actor는 `closed / None / 0 / None`을 보고합니다.
6. **영속, 만료 없음.** 시작만 하고 끝내지 못한 작업은 자리를 계속 쥡니다. 재시작을 넘어 영원히 쥡니다. `finish`나 `reset`까지입니다.

### 보장하지 않는 것

1. **자리에는 타임아웃이 없습니다.** 멈춘 작업(진행 중 표시가 남은 작업)은 이후의 모든 `begin`을 거절합니다. 명시적인 `finish`(결과를 아는 경우)나 `reset`(운영자의 결정)까지입니다. 라이브러리는 스스로 낫지 않습니다. `open` 뒤에 쉬는 시간 타이머도 없습니다.
2. **finish/reset의 소유권.** `actor`와 진행 중인 `job_id`를 아는 프로세스라면 무엇이든 `finish`나 `reset`을 할 수 있습니다. 이 값들은 인증되지 않습니다.
3. **`failures`는 교통을 막지 않습니다.** 실패를 몇 번 해도 `open` actor의 다음 `begin`은 언제나 회복 시도로 받아들여집니다.

### 장애 상황과 복구

| 상황 | 멈춘 뒤의 저장 상태 | 권장 복구 방법 |
|---|---|---|
| **작업 전에 멈춤**(`begin`은 성공했으나 작업은 시작하지 않음) | `pending = job_id`이고 상태는 `closed`입니다(회복 시도라면 `half_open`). 자리가 끼어 있습니다 | 아무것도 실행되지 않았음을 확인합니다 → `reset(actor, job_id)` → 다시 `begin`합니다 |
| **작업과 `finish` 사이에 멈춤**(작업은 어쩌면 끝났고 결과는 모름) | `pending = job_id`. 자리가 끼어 있습니다 | 실세계의 작업을 맞춰 봅니다. 완료를 확인했으면 `finish(actor, job_id, success=True)`를 부릅니다. 모르거나 실패했으면 `reset(actor)`(또는 `reset(actor, job_id)`)를 부릅니다 |
| **회복 시도(`half_open`) 중에 멈춤** | `half_open`이고 진행 중 표시가 있습니다 | 바로 위의 두 가지 방법과 같습니다 |
| 바쁨 대기 시간 초과 / 디스크 가득 / 네트워크 드라이브 | 변화 없음 / 부분 행 없음 / 보장 무효 | §1의 인프라 수준 장애를 보십시오 |

## 4. ReplayGuard

한 구성 요소 안에 독립된 도구 둘이 들어 있습니다.

* **안쪽(inbound)**(`requests` 표): `(principal, request_id)`마다 많아야 한 번 실행합니다. 저장되는 상태는 `pending`과 `completed`뿐입니다. `new`와 `conflict`는 `claim`이 돌려주는 판정(verdict)이지 저장되는 상태가 아닙니다.
* **바깥쪽(outbound)**(`outbound_requests` 표): 보내기 *전에* `intent_id`에 바뀌지 않는 `request_id`와 시각을 고정해 둡니다. 그래서 재시도는 받는 쪽에 하나의 요청으로 보입니다.

### 보장하는 것(안쪽)

1. **`claim`은 `(principal, request_id)`마다 정확히 한 번 `new`를 돌려줍니다.** 삽입은 기본 키로 보호됩니다(`ON CONFLICT DO NOTHING`). 판정 전체가 하나의 `BEGIN IMMEDIATE` 트랜잭션 안에서 계산됩니다. 경쟁하는 두 프로세스 중 정확히 하나만 `new`를 봅니다.
2. **이후의 claim은 다시 실행하지 않습니다.** 같은 `digest`면 `claim`은 `pending`(작업이 진행 중이거나 중단됨)이나 `completed`(저장된 응답을 재생)를 돌려줍니다. 다른 `digest`면 행을 건드리지 않고 `conflict`를 돌려줍니다.
3. **pending은 방치된 채로는 끝나지 않습니다.** `pending` 행이 `completed`로 가는 길은 맞는 `digest`로 `complete`/`apply_pending`을 부르는 것뿐입니다. 나이로 다시 실행되거나 풀리는 일은 없습니다. `complete`는 맞는 digest를 가진 pending 행에만 `(code, response)`를 저장합니다. 그때만 `True`를 돌려줍니다(이미 완료됨, digest 불일치, 모르는 쌍 → `False`). `code`는 `int`여야 합니다. `bool`은 트랜잭션이 열리기 전에 `TypeError`로 거절됩니다.
4. **`apply_pending`은 SQLite 안의 작업에 한해 정확히 한 번입니다.** `effect(connection)` 호출과 `UPDATE ... state='completed'`가 하나의 연결 위에서 하나의 트랜잭션 안에서 실행됩니다. 같이 커밋되거나 아예 커밋되지 않습니다(확인됨: 예외를 던지는 효과는 행을 pending으로 남기고 효과 자신의 쓰기까지 롤백합니다). 요청이 이 digest로 pending이 아니면 `None`을 돌려줍니다. 이때 효과는 실행되지 않습니다. 효과는 같은 인스턴스의 쓰기 메서드를 부르면 안 됩니다. `write_txn`이 겹쳐 쓰기를 `GuardError`로 거절합니다. 효과가 이 오류를 밖으로 흘려보내면 트랜잭션 전체가 롤백됩니다.
5. **`response`는 완료된 행만 재생합니다.** 맞는 digest를 가진 완료 행을 `(code, response_deserialized_from_json)`으로 돌려줍니다. 응답은 JSON으로 저장됩니다. 따라서 재생은 JSON 왕복입니다. 튜플은 목록으로 돌아옵니다. 문자열이 아닌 사전 키는 문자열로 돌아옵니다.

### 보장하는 것(바깥쪽)

1. **첫 예약이 이기고, 재시도는 같습니다.** `reserve_outbound`는 `intent_id` 기본 키 아래에 `fixed`와 생성한 `request_id`(uuid4 hex), `ts`를 `ON CONFLICT DO NOTHING`으로 삽입합니다. 이후 같은 `intent_id`를 쓰는 호출은 저장된 같은 컨텍스트를 돌려줍니다. 어떤 프로세스에서 하든, 무엇을 넘기든 마찬가지입니다.
2. **의도 재사용 감지.** 같은 `intent_id`에 다른 `fixed` 내용을 쓰면 `IntentMismatch`가 납니다. 이때 저장된 예약은 살아 남습니다. `fixed`는 `str → str`이어야 합니다(아니면 `TypeError`). `request_id`나 `ts`를 담으면 안 됩니다(`ValueError`).
3. **비밀값이나 본문은 저장하지 않습니다.** 저장되는 것은 넘긴 문자열 필드뿐입니다. 본문 대신 본문 해시를 `fixed`에 넣으십시오(문서 문자열의 약속입니다).

### 보장하지 않는 것

1. **SQLite 밖의 작업에는 정확히 한 번이 없습니다.** `claim`/`complete`는 "많아야 한 번"이라는 *결정*과 사람 손으로 하는 뒤처리의 묶음입니다. SQLite가 아닌 작업(HTTP 호출, 파일 쓰기, 서브프로세스)과 `complete` 사이에 멈추면 행은 `pending`으로 남습니다. 아무것도 다시 실행하지 않고, 되돌리지도 않습니다. 사용하는 쪽이 맞춰 봐야 합니다.
2. **pending에는 소유자도 임대도 나이도 없습니다.** 가드는 "다른 프로세스가 일하고 있다"와 "작업자가 죽었다"를 구분할 수 없습니다.
3. **`conflict`는 API 관점에서 끝입니다.** 행은 다른 digest의 재시도에 영원히 `conflict`로 답합니다. 지우거나 덮어쓰거나 리셋하는 API는 없습니다(모듈 안에 `DELETE`가 없습니다). 행은 라이브러리가 스스로 지우는 일이 전혀 없습니다.
4. **신원 확인.** principal은 받은 그대로 믿습니다. 신뢰할 수 있는 통신 경로(mTLS 신원, 검증된 서명)에서 와야 합니다.
5. **응답 직렬화(serialization).** `complete`는 트랜잭션을 열기 *전에* 응답을 JSON으로 바꿉니다. JSON으로 바꿀 수 없는 응답은 데이터베이스를 건드리지 않고 `TypeError`를 냅니다. 대신 요청은 `pending`으로 남습니다. 따라서 작업의 결과는 사람 손으로 맞춰야 합니다. 저장된 왕복은 타입을 그대로 보존하지 않습니다. 튜플은 목록으로 돌아옵니다. 문자열이 아닌 사전 키는 문자열로 돌아옵니다. `code`는 `int`여야 합니다(`bool`은 거절됩니다). 이 검사는 `complete`에서는 트랜잭션 전에, `apply_pending`에서는 그 안에 있습니다. 따라서 거기서 나쁜 `code`는 효과까지 롤백합니다.

### 장애 상황과 복구

| 상황 | 멈춘 뒤의 저장 상태 | 권장 복구 방법 |
|---|---|---|
| **`claim`(`new`) 후 작업 전에 멈춤** | 행은 `pending`입니다 | pending 요청을 사람 손으로 맞춥니다. 작업이 실행되지 않았음을 확인합니다 → 실행합니다 → 실제 `code`와 응답으로 `complete(...)`를 부릅니다 |
| **(외부) 작업과 `complete` 사이에 멈춤** | 행은 `pending`입니다. 작업의 결과는 모릅니다 | 밖에서 맞춥니다(하위 시스템의 기록을 확인합니다, 고정해 둔 `request_id`를 받는 쪽의 멱등 키로 씁니다) → 실제 결과로 `complete(...)`를 부릅니다. **조용히 다시 실행하지 않습니다** |
| **진행 중에 중복 요청이 도착** | 행은 `pending`입니다. `claim`은 `pending`을 돌려줍니다 | 다시 실행하지 말고 "나중에 다시 시도"로 답합니다. 완료되면 `response()`가 저장된 답을 돌려줍니다 |
| **다른 내용으로 재시도** | 행은 변하지 않습니다. `claim`은 `conflict`를 돌려줍니다 | 요청을 거절합니다. digest가 왜 바뀌었는지 알아봅니다. conflict를 지우는 API는 없습니다 |
| **`reserve_outbound` 후 보내기 전에 멈춤** | 의도는 예약되었습니다. `request_id`는 고정되어 있습니다 | 같은 `intent_id`로 보내기를 다시 하면 됩니다. 같은 `request_id`이므로 받는 쪽의 중복 제거가 적용됩니다 |
| **보낸 후 자기 기록 전에 멈춤** | 예약은 보내기 *전에* 쓰였습니다. 따라서 다시 보내기도 같은 `request_id`를 갖습니다 | 안전하게 다시 보냅니다. 받는 쪽은 `request_id`로 중복을 제거합니다 |
| **SQLite 전용 작업 + 멈춤** | 작업과 `completed` 행이 같이 커밋되었거나, 둘 다 없습니다(확인됨) | 맞출 것이 없습니다. `claim`/`response`로 확인합니다 |
| 바쁨 대기 시간(기본 15초) / 디스크 가득 / 네트워크 드라이브 | 변화 없음 / 부분 행 없음 / 보장 무효 | §1의 인프라 수준 장애를 보십시오. 작업 중간에 멈추면 위의 맞춤 절차가 추가로 필요할 수 있습니다 |

## 5. 올바른 도구 고르기

| 필요한 것 | 쓸 도구 | 일부러 제공하지 않는 것 |
|---|---|---|
| "자원 X를 다시 시작을 넘어 한 번에 하나의 작업만 만지게 하고 싶습니다" | `ResourceLock` | 죽은 잠금자 감지, 임대(lease), 울타리 토큰 |
| "작업자마다 진행 중인 작업은 하나, 실패 뒤 회복 시도는 하나" | `CircuitBreaker` | 차단 임계값, 쿨다운 타이머, 자리 타임아웃 |
| "이 안쪽 요청을 많아야 한 번 처리하고, 재생에는 저장된 답을 주고 싶습니다" | `ReplayGuard.claim` / `complete` / `response` | pending 요청의 재실행이나 만료 |
| "작업과 기록된 결과가 같이 커밋되어야 합니다" | `ReplayGuard.apply_pending`(SQLite 전용 작업) | 파일, 네트워크, 서브프로세스에 대한 원자성 |
| "이 바깥쪽 요청을 의도당 많아야 한 번 보내고 싶습니다" | `ReplayGuard.reserve_outbound` | 본문이나 비밀값의 저장 |
| "사람이 확인한 뒤 죽은 잠금자/끼인 자리/pending 요청을 치우고 싶습니다" | `break_lock` / `reset` / `complete` | 이들 가운데 무엇의 자동 만료 |
| "오래된 상태를 N초 뒤에 자동으로 만료하고 싶습니다" | — 여기에는 없습니다 — | 이것이 라이브러리의 핵심 설계 결정입니다 |
